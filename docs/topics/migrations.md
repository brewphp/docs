# Migrations

**Migrations** keep your database schema in step with your models. You
change a model, run `makemigrations`, and BrewPHP writes a small PHP file
that describes the change. `migrate` then applies that file to the
database. It works like Django's migrations, and the commands have the same
names.

Migration files live in each app's `migrations/` folder and belong in git.
Every developer, CI job and server applies the same files in the same
order, so every database ends up with the same tables.

## The workflow

```bash
php manage.php startapp blog          # 1. create an app
#    add 'blog' to INSTALLED_APPS, write models in apps/blog/models.php
php manage.php makemigrations         # 2. write migration files from the models
php manage.php migrate                # 3. apply them to the database
```

`startapp` creates the app with an empty `migrations/` folder (see
[Project structure](../getting-started/project-structure.md#creating-an-app)).
Then write your models:

```php title="apps/blog/models.php"
final class Author extends Model
{
    public static function fields(): array
    {
        return [
            'name' => new Fields\CharField(maxLength: 100),
        ];
    }
}

final class Post extends Model
{
    public static function fields(): array
    {
        return [
            'title' => new Fields\CharField(maxLength: 200, helpText: 'The headline'),
            'body' => new Fields\TextField(blank: true),
            'author' => new Fields\ForeignKey(Author::class, onDelete: OnDelete::Cascade, relatedName: 'posts'),
            'published_at' => new Fields\DateTimeField(null: true, blank: true),
            'created_at' => new Fields\DateTimeField(autoNowAdd: true),
        ];
    }
}
```

`makemigrations` compares the models with the existing migrations and
writes the difference:

```text
$ php manage.php makemigrations
Migrations for "blog":
  apps/blog/migrations/0001_initial.php
    - Create model Author
    - Create model Post
Run "php manage.php migrate" to apply them.
```

`migrate` applies every migration that has not run yet:

```text
$ php manage.php migrate
Operations to perform:
  Apply all migrations: blog
Running migrations:
  Applying blog.0001_initial... OK
```

From now on, every change to a model follows the same two steps:
`makemigrations`, then `migrate`. Review the new file before you commit it.

!!! tip "See the SQL"
    `php manage.php sqlmigrate blog 0001` prints the SQL of a migration
    without running it. See [manage.php](../cli/overview.md#sqlmigrate).

## Migration files

This is the file `makemigrations` wrote for the models above:

```php title="apps/blog/migrations/0001_initial.php"
<?php

declare(strict_types=1);

use BrewPHP\Db\Fields;
use BrewPHP\Db\Migrations\Migration;
use BrewPHP\Db\Migrations\Operations;

// Generated by BrewPHP 0.4.0-dev on 2026-10-15 17:18.

return new class extends Migration
{
    public bool $initial = true;

    public function operations(): array
    {
        return [
            new Operations\CreateModel(
                name: 'Author',
                fields: [
                    'id' => new Fields\BigAutoField(),
                    'name' => new Fields\CharField(maxLength: 100),
                ],
                table: 'blog_author',
            ),
            new Operations\CreateModel(
                name: 'Post',
                fields: [
                    'id' => new Fields\BigAutoField(),
                    'title' => new Fields\CharField(maxLength: 200),
                    'body' => new Fields\TextField(),
                    'author' => new Fields\ForeignKey(to: 'blog.Author'),
                    'published_at' => new Fields\DateTimeField(null: true),
                    'created_at' => new Fields\DateTimeField(),
                ],
                table: 'blog_post',
            ),
        ];
    }
};
```

A migration file returns an object of an anonymous class that extends
`BrewPHP\Db\Migrations\Migration`. It has:

| Member | Meaning |
|---|---|
| `operations()` | The list of [operations](#operations), run in order. |
| `public array $dependencies` | Migrations that must run first, as `"app.name"` strings. |
| `public bool $initial` | `true` for the first migration of an app. |
| `public bool $atomic` | Run the migration in one transaction (default `true`; see [Transactions](#transactions)). |

The file name is the migration's name: four digits, an underscore and a
name in lower-case letters, digits and underscores, such as
`0002_post_subtitle.php`. Other files in the folder (such as `.gitkeep`)
are ignored. The app label comes from the folder, so a migration is known
as `blog.0002_post_subtitle`.

### Dependencies

`$dependencies` lists the migrations that must be applied before this
one, as `"app.name"` strings:

```php
public array $dependencies = [
    'blog.0001_initial',
    'shop.0003_product_sku',
];
```

`makemigrations` fills it in for you. A new migration depends on the
latest migration of its own app, and on the latest migration of every
other app whose models its foreign keys point at. `migrate` sorts all
migrations so that dependencies always run first. A dependency that does
not exist is an error:

```text
✘ Migration blog.0002_post_tags depends on shop.0001_initial, which does not exist. Is the app installed and the migration file present?
```

### Names

`makemigrations` names the first migration of an app `initial`. Later
migrations get a name built from their operations, such as
`0002_post_subtitle` or `0003_remove_post_body`. A long or unclear name
becomes `auto_<date>_<time>`. Choose your own name with `--name`:

```bash
php manage.php makemigrations blog --name=add_subtitle
```

Names may only contain lower-case letters, digits and underscores (at most
80 characters).

## What is recorded

Migrations record only what changes the database: table names, columns,
column types, `null`, `unique`, `dbIndex`, `primaryKey`, `dbColumn`, a
plain `default`, foreign key targets and indexes. In the file above,
`helpText`, `blank`, `onDelete`, `relatedName` and `autoNowAdd` are
missing on purpose.

Changing one of these options needs **no migration**:

| Option | Why |
|---|---|
| `helpText`, `verboseName`, `choices`, `blank`, `editable`, `validators` | Validation, forms and the admin only |
| `onDelete`, `relatedName` (`ForeignKey`, `OneToOneField`) | `OnDelete` rules are applied in PHP |
| `autoNow`, `autoNowAdd` (date and time fields) | Values are set in PHP when saving |
| a closure `default` (`default: fn () => []`) | Called in PHP for each new object |

Model options such as `ordering()`, `verboseName()` and
`verboseNamePlural()` are not recorded either. `table()` and `indexes()`
are.

!!! note "Defaults"
    A plain default is recorded because it is useful when a column is added
    to a table that has rows. A backed enum default is recorded as its
    value. A closure default is left out, so adding a non-null field whose
    default is a closure works like a field without a default (see
    [One-off defaults](#one-off-defaults)).

## Changing models

Each change to your models becomes one or more operations. Add a field:

```text
$ php manage.php makemigrations
Migrations for "blog":
  apps/blog/migrations/0002_post_subtitle.php
    - Add field subtitle to Post
Run "php manage.php migrate" to apply them.
```

Several changes in one run go into one migration per app. Inside a
migration, operations are ordered so that each one works: renames first,
then new models, removed indexes, renamed, added, changed and removed
fields, new indexes, and deleted models last. New models are created
before the models that point at them; when two new models point at each
other, one of the foreign keys is added after both tables exist.

### Renames

`makemigrations` cannot see a rename. It sees a field that disappeared and
another that appeared. When both have the same definition, it asks:

```text
$ php manage.php makemigrations
Was Post.title renamed to Post.headline? [y/N]: y
Migrations for "blog":
  apps/blog/migrations/0002_rename_title_post_headline.php
    - Rename field title on Post to headline
Run "php manage.php migrate" to apply them.
```

Answer `y` to keep the data: the migration renames the column. Answer `n`
(or press Enter) and the migration drops the old column and adds a new one,
**losing its data**.

A renamed model works the same way. When a removed model and a new model
have the same fields, `makemigrations` asks
`Was the model blog.Post renamed to Article?`. A confirmed rename writes a
`RenameModel` operation, plus an `AlterModelTable` when the table name
changes too (the default table name `blog_post` becomes `blog_article`).

!!! warning "Renames without questions"
    With `--no-interaction` (and with `--check`), `makemigrations` never
    assumes a rename. A renamed field becomes a removed field and a new
    field. Run `makemigrations` interactively when you rename something, and
    read the new migration before you apply it.

### One-off defaults

A new field that cannot be null and has no default needs a value for the
rows already in the table. `makemigrations` asks for one:

```text
$ php manage.php makemigrations
The new field Post.slug cannot be null and has no default. Value for existing rows (a number, true/false or text): 'hello'
Migrations for "blog":
  apps/blog/migrations/0002_post_slug.php
    - Add field slug to Post
Run "php manage.php migrate" to apply them.
```

Answer with a number (`0`, `1.5`), `true` or `false`, or text (quotes are
optional). An empty answer is asked again, up to three times. The value is
written with `preserveDefault: false`:

```php
new Operations\AddField(model: 'Post', name: 'slug', field: new Fields\SlugField(default: 'hello'), preserveDefault: false),
```

The default fills the existing rows when the migration runs. It is not
kept in the migration state, so your model still has no default and the
next `makemigrations` finds no changes.

When a field that allowed `NULL` becomes non-null without a default,
`makemigrations` asks for a value for the rows that are `NULL`. An empty
answer means "none": the migration is written without a value, and
`migrate` fails if any row is still `NULL`.

!!! note "`--no-interaction`"
    Without questions, `makemigrations` refuses to guess a value for a new
    non-null field and stops:

    ```text
    ✘ Cannot add the non-nullable field "slug" to Post without a default: existing rows need a value. Give the field a default or null: true, or run makemigrations interactively to provide a one-off value.
    ```

    For a field that becomes non-null, it writes the migration without a
    value.

### Editing migrations

Migration files are plain PHP. You can edit a generated file, or write one
by hand, as long as it still describes your models: after your changes,
`makemigrations` should report `No changes detected.`.

Start a hand-written migration with `--empty`. It needs the app and
depends on the app's latest migration:

```bash
php manage.php makemigrations blog --empty --name=fill_slugs
```

```php title="apps/blog/migrations/0003_fill_slugs.php"
return new class extends Migration
{
    public array $dependencies = [
        'blog.0002_post_slug',
    ];

    public function operations(): array
    {
        return [];
    }
};
```

!!! warning "Applied migrations"
    Don't edit a migration that has already been applied on another
    machine: that database will never run your new version. Write a new
    migration instead.

## Operations

Operations are classes in `BrewPHP\Db\Migrations\Operations`. Generated
files import the namespace (`use BrewPHP\Db\Migrations\Operations;`) and
the field classes (`use BrewPHP\Db\Fields;`), and write
`new Operations\AddField(...)`. Model names are names inside the
migration's app (`'Post'`), and fields are passed as field objects.

| Operation | What it does |
|---|---|
| `CreateModel(string $name, array $fields, string $table, array $indexes = [])` | Creates a table. `$fields` maps names to fields, primary key first; `$indexes` is a list of `BrewPHP\Db\Index`. Undo: drops the table. |
| `DeleteModel(string $name)` | Drops a table. Undo: creates it again, empty. |
| `RenameModel(string $oldName, string $newName)` | Renames a model in the migration state and points foreign keys at the new name. The table keeps its name. |
| `AlterModelTable(string $name, string $table)` | Renames a model's table. |
| `AddField(string $model, string $name, Field $field, bool $preserveDefault = true)` | Adds a column. With `preserveDefault: false` the default only fills existing rows. Undo: drops the column. |
| `RemoveField(string $model, string $name)` | Drops a column. Undo: adds it back, empty; a non-null field then needs a default if the table has rows. Fails while an index uses the field. |
| `AlterField(string $model, string $name, Field $field, bool $preserveDefault = true)` | Changes a column: type, `null`, `unique`, index or foreign key target. With `preserveDefault: false` the default only fills rows that are `NULL`. |
| `RenameField(string $model, string $oldName, string $newName)` | Renames a field and its column (unless the column is set with `dbColumn`). Indexes on the field are dropped and created again, so their generated names follow the new column name. |
| `AddIndex(string $model, Index $index)` | Creates an index from `indexes()`. |
| `RemoveIndex(string $model, Index $index)` | Drops an index. The index is matched by its fields, name and uniqueness. |
| `RunSQL($sql, $reverseSql = null)` | Runs raw SQL: one statement as a string, or a list of statements. See [Data migrations](#data-migrations). |
| `RunPHP(callable $forwards, ?callable $backwards = null, string $description = 'PHP operation')` | Runs PHP code. See [Data migrations](#data-migrations). |

Every operation except `RunSQL` and `RunPHP` without a backwards part can
be undone, so most migrations can be [unapplied](#moving-backwards).

Operations work on the **migration state**: the models as the migrations
before them describe them, not your current model classes. A migration
written a year ago still creates the table as it was a year ago, even if
the model has changed since.

## Data migrations

Some changes need more than a schema change: filling a new column from an
old one, or fixing rows. Write these by hand in an empty migration with
`RunSQL` or `RunPHP`. `makemigrations` never writes them.

### RunSQL

`RunSQL` runs SQL statements as written. Pass one statement as a string,
or several as a list:

```php
new Operations\RunSQL(
    "UPDATE blog_post SET status = 'draft' WHERE status IS NULL",
    reverseSql: [],
),
```

`reverseSql` is what undoing the migration runs:

| `reverseSql` | Undoing the migration |
|---|---|
| `null` (the default) | is impossible: the migration is irreversible |
| `[]` | does nothing (a no-op) |
| a string or a list | runs those statements |

`sqlmigrate` shows the SQL of `RunSQL` operations. The SQL is not
translated between engines, so write SQL that works on the databases you
use.

### RunPHP

`RunPHP` runs PHP code, like Django's `RunPython`. The callables receive
the connection (`BrewPHP\Db\Connection`) and the migration state
(`BrewPHP\Db\Migrations\ProjectState`) at that point:

```php title="apps/blog/migrations/0003_fill_slugs.php"
<?php

declare(strict_types=1);

use BrewPHP\Db\Connection;
use BrewPHP\Db\Migrations\Migration;
use BrewPHP\Db\Migrations\Operations;
use BrewPHP\Db\Migrations\Operations\RunPHP;
use BrewPHP\Db\Migrations\ProjectState;

return new class extends Migration
{
    public array $dependencies = [
        'blog.0002_post_slug',
    ];

    public function operations(): array
    {
        return [
            new Operations\RunPHP(
                static function (Connection $db, ProjectState $state): void {
                    $table = $state->get('blog', 'Post')->table;
                    foreach ($db->select("SELECT id, title FROM $table") as $row) {
                        $slug = strtolower(trim((string) preg_replace('/[^A-Za-z0-9]+/', '-', $row['title']), '-'));
                        $db->statement("UPDATE $table SET slug = ? WHERE id = ?", [$slug, $row['id']]);
                    }
                },
                backwards: RunPHP::noop(...),
                description: 'Fill Post.slug from the title',
            ),
        ];
    }
};
```

- Without `backwards`, the migration cannot be unapplied. Pass
  `RunPHP::noop(...)` when undoing needs no work.
- `description` is shown by `migrate --plan` and `sqlmigrate`.
- `sqlmigrate` cannot show the SQL that PHP code runs; it prints only the
  description.

!!! tip "Use the state, not your models"
    Read table and column names from the state:
    `$state->get('blog', 'Post')->table` gives the table name, and
    `$state->meta('blog', 'Post')->field('author')->column` gives a column
    (`author_id`). Avoid your current model classes in migrations: the
    models will change later, but the migration must keep working as
    written.

## Transactions

On **SQLite and PostgreSQL**, each migration runs in one transaction. If an
operation fails, the whole migration is rolled back, and it is not
recorded as applied. Fix the problem and run `migrate` again.

**MySQL and MariaDB** cannot roll back schema changes: each `CREATE`,
`ALTER` or `DROP` is committed at once. A migration that fails halfway
leaves the operations before the failure in place, and is not recorded.
Keep MySQL migrations small, and fix such a database by hand before you
retry.

To run one migration without a transaction (for example a large data
migration that commits in batches), opt out:

```php
return new class extends Migration
{
    public bool $atomic = false;

    // ...
};
```

!!! note "Foreign keys on SQLite"
    Changing a table on SQLite often means rebuilding it (see
    [The schema editor](models.md#the-schema-editor)). So during a
    migration's transaction, BrewPHP turns SQLite's foreign key checks off.
    Before committing, it runs `PRAGMA foreign_key_check`. If any row breaks
    a foreign key, the migration is rolled back:

    ```text
    ✘ Migration blog.0004_fix_authors left rows that break foreign key constraints.
    ```

    The checks are turned on again afterwards.

## The migrations table

`migrate` records every applied migration in the `brewphp_migrations`
table, with its app, its name and when it was applied (UTC). The table is
created by the first `migrate` that applies something. This is how
`migrate` knows what still has to run, and how `showmigrations` shows
`[X]` and `[ ]`:

```text
$ php manage.php showmigrations
blog
 [X] 0001_initial
 [ ] 0002_post_slug
```

Don't edit this table by hand; use `migrate --fake` instead.

## Running migrations

| Command | What it does |
|---|---|
| `migrate` | Applies every migration of every app. |
| `migrate blog` | Applies the migrations of `blog`, and those they depend on. |
| `migrate blog 0002` | Moves `blog` forwards or backwards so that `0002_...` is its latest applied migration. |
| `migrate blog zero` | Unapplies every migration of `blog`. |
| `migrate --plan` | Shows what would run, and runs nothing. |
| `migrate --fake` | Records (or unrecords) migrations without running them. |

A migration name can be shortened to any prefix that matches one
migration, usually its number: `0002` for `0002_post_slug`.

`migrate` warns when your models have changes that no migration describes
yet:

```text
! Your models in app(s) blog have changes that are not yet reflected in a migration. Run "php manage.php makemigrations".
```

### Moving backwards

Name an earlier migration to undo the ones after it:

```text
$ php manage.php migrate blog 0001
Operations to perform:
  Target blog.0001_initial
Running migrations:
  Unapplying blog.0002_post_slug... OK
```

Migrations of other apps that depend on an unapplied migration are
unapplied first. `zero` unapplies everything of an app:

```bash
php manage.php migrate blog zero
```

Undoing runs each operation's reverse, last operation first. A migration
with an irreversible operation (`RunSQL` without `reverseSql`, `RunPHP`
without `backwards`) stops the command:

```text
✘ Migration blog.0003_fill_slugs cannot be unapplied: "Raw SQL operation" is not reversible.
```

!!! warning "Data loss"
    Unapplying a migration that created a table or added a column drops it,
    with its data. Unapplying `DeleteModel` or `RemoveField` brings back an
    empty table or column, not the old data.

### --plan

`--plan` lists the migrations and operations that would run:

```text
$ php manage.php migrate --plan
Planned operations:
blog.0001_initial
    Create model Author
    Create model Post
```

When moving backwards, each migration is marked `(unapply)`, and its
operations are listed in the order they are undone, last one first:

```text
$ php manage.php migrate blog 0001 --plan
Planned operations:
blog.0002_rename_title_post_headline_post_slug (unapply)
    Undo add field slug to Post
    Undo rename field title on Post to headline
```

### --fake

`--fake` marks migrations as applied (or unapplied) in
`brewphp_migrations` without touching the tables. Use it when the database
already matches the migrations, for example tables created before you
used migrations:

```text
$ php manage.php migrate blog 0001 --fake
Operations to perform:
  Target blog.0001_initial
Running migrations:
  Applying blog.0001_initial... FAKED
```

!!! warning
    `--fake` trusts you. If the tables don't match the migrations, later
    migrations fail or change the wrong thing.

### Another database

`migrate`, `showmigrations` and `sqlmigrate` use the `default` connection.
Pass `--database=NAME` to use another connection from `DATABASES`; each
database has its own `brewphp_migrations` table.

## Conflicts

Two developers can each add a migration to the same app on their own
branch, for example `0003_post_tags` and `0003_post_summary`. Both depend
on `0002`. After merging, the app has two latest migrations. `migrate`
refuses to run (and exits with `1`) until the conflict is fixed, and
`makemigrations` stops too:

```text
✘ Conflicting migrations in app "blog": blog.0003_post_summary and blog.0003_post_tags. Run "php manage.php makemigrations --merge" to merge them.
```

Fix it with `makemigrations --merge`, like Django's:

```text
$ php manage.php makemigrations --merge
Migrations for "blog":
  apps/blog/migrations/0004_merge_0003_post_summary_0003_post_tags.php
    - Merge blog.0003_post_summary, blog.0003_post_tags
Run "php manage.php migrate" to apply them.
```

For each app with more than one latest migration (or only the apps you
name), it writes a **merge migration**: a migration with no operations
that depends on every latest migration. The name is `merge_` followed by
their names, or `merge_<date>_<time>` when that would be too long. When no
app has a conflict, it prints `No conflicts detected to merge.`

```php title="apps/blog/migrations/0004_merge_0003_post_summary_0003_post_tags.php"
<?php

declare(strict_types=1);

use BrewPHP\Db\Migrations\Migration;

// Generated by BrewPHP 0.4.0-dev on 2026-10-15 17:27.

return new class extends Migration
{
    public array $dependencies = [
        'blog.0003_post_summary',
        'blog.0003_post_tags',
    ];

    public function operations(): array
    {
        return [];
    }
};
```

Commit it, then run `migrate`. A database that already applied one of the
two branches simply applies the other one and the merge migration. A merge
migration written by hand works exactly the same way.

The numbers don't matter for the order; only the dependencies do. The
merge migration does not look at what the two branches change: if both
change the same field, check that they still make sense together. A
circular dependency between migrations is an error too.

## Inconsistent history

Before running anything, `migrate` checks that every applied migration's
dependencies are applied too. If not, it stops, even with `--fake`:

```text
✘ Inconsistent migration history: blog.0003_post_tags is applied before its dependency blog.0003_post_summary.
```

This usually means the dependencies of a migration were edited after it
was applied, for example to fix a [conflict](#conflicts) by hand on a
database where only one of the two migrations had run. Put the
dependencies back as they were and run `makemigrations --merge` instead.

## After migrating

Every app can react to `migrate` by overriding `AppConfig::migrated()`,
like Django's `post_migrate` signal. It is called for every installed app
after each successful `migrate`, even when there was nothing to apply.
The tables of every applied migration exist by then, so it is a good place
to create rows the app needs:

```php title="apps/blog/App.php"
use Apps\Blog\Category;
use BrewPHP\Core\AppConfig;
use BrewPHP\Core\Application;

final class App extends AppConfig
{
    public function migrated(Application $app): void
    {
        Category::objects()->getOrCreate(['slug' => 'general'], ['name' => 'General']);
    }
}
```

Because it runs after every `migrate`, write it so that running it twice
does no harm (`getOrCreate()`, not `create()`). It is not called when
`migrate` fails.

## In CI

`makemigrations --check` writes nothing. It exits with `1` when your models
have changes that no migration describes, and lists them:

```yaml title=".github/workflows/tests.yml"
- run: php manage.php makemigrations --check
- run: php manage.php migrate --no-interaction
```

This catches a model change that was committed without its migration.
Then `migrate` applies the migrations to the CI database, so your tests
run against the same schema as production.

## Security

- **Generated files hold only plain values.** The writer writes strings,
  numbers, booleans, `null`, arrays, enum cases, fields and indexes, and
  writes every string through `var_export()`. A default such as
  `"'); system('...'); //"` stays a string; it cannot become code. Other
  values (objects, closures) cannot be written, and `makemigrations` stops
  with an error.
- **Names are validated.** `--name` accepts only lower-case letters,
  digits and underscores, so a name like `../../evil` is rejected and no
  file is written outside the app's `migrations/` folder. Existing files
  are never overwritten.
- **Migrations are only written into your project.** `makemigrations`
  never writes into the framework or into a Composer package in
  `vendor/`. If such an app's models differ from its migrations, the
  command stops and asks you to check your versions.
- **`RunSQL` runs as written.** Never build its SQL from user input or
  other data you don't control. In `RunPHP`, use placeholders
  (`$db->statement($sql, [$value])`) for values.
- **Migration files are code.** `migrate` runs them with `require`.
  Review migration files in pull requests like any other code.

## Limitations

BrewPHP's migrations cover the common cases. Some things Django does are
not there yet:

- **No squashing.** There is no `squashmigrations`; long histories stay as
  they are.
- **Renamed tables keep old constraint names.** When a table is renamed
  (`AlterModelTable`, or a renamed model), the foreign key constraints and
  indexes keep the names generated from the old table name, such as
  `blog_post_author_id_96f44456_fk`. This is harmless, but the names no
  longer match the table.
- **Merges don't compare changes.** `makemigrations --merge` only joins
  the branches; unlike Django, it does not show what each branch changes
  or warn when both change the same model (see [Conflicts](#conflicts)).
